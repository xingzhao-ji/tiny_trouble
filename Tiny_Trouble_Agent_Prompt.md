# Tiny Trouble Autonomous Development Prompt

Attach this file together with Tiny_Trouble_Design_Bible.md to the coding agent that will build the game. The design bible defines the game, campaign, visual standard, milestone gates, and acceptance criteria. This prompt instructs that agent to implement the project. It does not claim that a game is already built or that this document starts a background process.

## The one overriding work condition

**Keep developing and perfecting Tiny Trouble throughout the authorized execution window: repeatedly inspect the playable build, choose the highest-priority in-scope improvement, implement it, test and visually inspect the result, preserve a working checkpoint, and immediately continue to the next approved task. Do not stop because a prototype, test suite, milestone, or campaign has been completed, and do not ask for routine permission to continue. Continue productive work for as long as actual execution and usage remain available, unless the user stops you or a genuine permission or capability blocker prevents all useful progress. Respect platform limits; never evade a stop, invent remaining quota, or claim work continues after execution ends.**

## Your assignment

Act as the project's implementation owner, gameplay programmer, technical artist, level designer, audio implementer, and QA coordinator. Produce a real, runnable game with source assets and evidence of its behavior. The user's intended role is creative direction and play feedback, not manually assembling the generated components.

Read the attached design bible, especially Binding project goals and scope, Locked art direction and visual acceptance, First milestone specification, and Ordered milestones and continuous work. Inspect the existing repository and applicable instructions before making changes. Preserve existing work and a suitable established stack. Use tools and capabilities that actually exist in your environment.

Begin implementation in the current authorized session. A plan, attractive screenshot, mock menu, scene file collection, or generated concept sheet alone is not the requested result. Keep planning proportional to the decision it enables, then build and inspect the playable experience.

## Locked game identity

- Solo stylized 3D puzzle adventure through household dioramas, with fixed or gently guided three-quarter cameras.
- Pip, a small expressive handmade creature, resizes eligible props among small, normal, and large states with clear authored consequences.
- Visual direction: polished crafted toys, rounded silhouettes, resin/fabric/paper/wood/ceramic materials, soft lighting, strong contact, readable interactions, and expressive animation.
- Campaign destination: the twelve named worlds and exactly sixty main stages in the design bible. World 12 contains the finale; the Matchbox Workshop is the hub.
- First integrating milestone: VS01 Toast Express Demo, with six principal prop families, three connected puzzles, one optional discovery, and the toast-launch finale specified in the bible.
- Every required puzzle works for one player. Local or online multiplayer is deferred and must not divert campaign development.
- No unrelated genres, procedural campaign replacement, live AI companion system, crafting trees, monetization, account system, or extra campaign settings.

Treat these as project boundaries. You may solve implementation and design details autonomously within them. Put unrelated ideas in a deferred list and return to approved work. Preserve the core mechanic and art direction when resolving technical constraints.

## First actions

1. Inspect the project, working instructions, installed runtime, graphics/capture capabilities, existing assets, and existing changes. If no repository exists, create an appropriate local project with versioned checkpoints through the supported workflow.
2. Establish reproducible launch and build commands. Prefer Godot when it can actually run and be inspected; preserve a suitable existing implementation. Document any necessary alternative and its limitations.
3. Create the reference art sheet and representative target frame, then begin a minimal in-engine scene with Pip, movement, targeting, resizing, and local reset.
4. Implement the spoon bridge, blueberry/cereal-flap ballast, butter-pat latch, napkin landing preparation, and toaster release sequence from VS01. Reuse the blueberry after the latch makes the previous route persistent.
5. Replace temporary visuals, complete the required feedback, validate recovery and save boundaries, and capture the demo's six fixed review views and an actual playthrough when possible.
6. When the demo passes its gates, continue directly to the five-stage Breakfast Chapter and minimal workshop, then to the remaining worlds in the approved order.

The in-engine screenshot must be distinguished from concept art. Only genuine executed checks support claims that the game runs, a route works, audio was auditioned, or a performance target was met.

## Continuous improvement loop

Maintain one integrating milestone. For each iteration:

1. Read the current state, known issues, and gate failures. Inspect the affected build or scene when useful.
2. Choose one concrete task. Record its parent milestone, requirement, observed need, expected player benefit, scope limit, and acceptance check.
3. Implement a coherent change. Delegate independent bounded subtasks when supported and useful; one owner integrates and reviews them.
4. Run targeted checks and replay the affected route. Broaden testing only for a remaining risk or a required milestone gate.
5. Inspect actual output. Check visual consistency, camera behavior, interaction feedback, recovery, and relevant measured performance.
6. Retain a verified improvement, revise an incomplete result, or roll back a regression. Do not mistake a change for an improvement.
7. Preserve source, editable assets, a usable build or precise build instructions, and a short evidence record. Update the next task and continue immediately while execution is available.

Prioritize save loss and crashes, blocked progression, controls and recovery, current milestone omissions, art-contract failures, weak feedback and puzzle clarity, then the next approved stage. New content follows existing quality gates. Once the 60-stage campaign is stable, work through approved optional variants and sandbox/photo features; then keep refining demonstrated weaknesses in the same game.

Do not create filler commits, cosmetic renaming campaigns, repetitive unchanged test loops, speculative framework migrations, or new features simply to occupy remaining usage. If the queue is empty, audit an under-reviewed quality dimension and act on concrete findings.

## Art expectations

Produce the art reference sheet, target frame, actual in-engine comparison, complete principal prop states, required Pip animations, supporting environment kit, UI, effects, and available audio. Use the bible's fixed palette and material/shape language as the starting standard. Preserve editable assets and generation provenance.

Review the opening, each of the three puzzles, optional discovery, and finale from consistent views. Completed milestones have no visible placeholders, missing materials, debug overlays, illegible prompts, obvious intersections, distracting flicker, or unexplained differences in asset style. Resizing must look and feel intentional. The main route and important targets remain readable.

Use available image generation, procedural geometry, animation, synthesis, and editing tools for the asset types they actually support. A raster image is not automatically a rigged 3D model. If a capability is missing, make a coherent supported substitute or leave an explicit unverified item and continue other useful work. Do not fabricate successful asset production or review.

World-class visual quality is the ambition. Technical checks establish completeness and consistency; aesthetic appeal and enjoyment remain human judgments. Do not pause all development waiting for optional feedback. Record the pending human review and continue on objective issues or the next approved task.

## Progress records and resumption

Maintain a small durable record set in the repository, adapted to existing conventions:

- PROJECT_STATE.md: active milestone, current build status, decisions, exact launch commands, next three tasks.
- BACKLOG.md: prioritized in-scope work, requirement mapping, blockers, and deferred ideas.
- QUALITY_REPORT.md: passed/failed/unverified gates, evidence paths, measured conditions, and known limitations.
- ART_DIRECTION.md and ASSET_MANIFEST: current reference decisions, asset IDs, editable sources, provenance, and unresolved substitutions.

Commit coherent working changes when appropriate to the repository workflow. Preserve a known-good build before risky changes and guard save-format compatibility. Do not overwrite unrelated user changes. Progress notes should state what changed, what was checked, what remains uncertain, and what comes next. They are checkpoints rather than requests for permission.

Remaining quota or execution time may not be visible. Do not promise to stop at an invented exact balance. Save useful checkpoints after meaningful work so an abrupt platform limit does not erase progress. If a genuine blocker affects only one task, choose another useful approved task. When execution actually ends or the user stops you, leave the latest stable state and precise resume instructions if the environment still permits it.

This directive does not authorize paid usage beyond the account's existing authorized limits, purchases, public publishing, messages to others, approval bypasses, or replacement processes intended to evade a stop. It authorizes sustained, productive development of this game during available execution. Do not claim an infinite background run has begun.

**Start with the current milestone and keep building.**
